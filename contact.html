Contact

Report a bug, accessibility barrier, documentation error, security concern, or partnership question through a monitored channel.

What to send

Bug reports, documentation corrections, accessibility barriers, advertising or partnership inquiries, and responsible security reports are welcome. A useful bug report names the page, browser and operating system, steps to reproduce, expected result, and actual result. Share only a small example that contains no secrets or personal information.

For accessibility feedback, describe the control or reading order that caused difficulty and the assistive technology used if you are comfortable sharing it. For a security report, put SECURITY in the subject line and avoid a public issue when the details could enable abuse.

Email

Write to wuyung027@gmail.com. Messages are normally reviewed within two to three business days. Complex technical reports may take longer to investigate, but concise reproduction steps help substantially.

GitHub Issues

Use GitHub Issues for non-sensitive bugs and feature requests. Search existing issues first, use a descriptive title, and keep confidential data out of screenshots, code samples, and logs.

A note about private material

The tools are designed so editor inputs stay in your browser, but an email or public issue is a separate communication channel. Do not attach passwords, API keys, customer records, private documents, proprietary source code, or unredacted logs. Replace sensitive values with a harmless sample that still reproduces the problem.

What happens next

Reports are triaged by impact and reproducibility. A confirmed functional or accessibility defect may lead to a code change and an updated page date. Feature suggestions are considered against the collection’s focus on small, local, account-free utilities; sending a suggestion does not guarantee implementation.
