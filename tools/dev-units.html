Web units, color formats, and Unix time

REM vs PX: choosing a sizing system that scales

Pixels and root ems solve different problems. A CSS pixel is a reference unit defined as 1/96 of an inch; it is not always one physical screen pixel. On high-resolution screens one CSS pixel covers several device pixels, and window.devicePixelRatio reports that ratio. A px value is therefore stable within the CSS layout coordinate system, which makes it useful for fine borders and details that should keep a fixed CSS size.

A rem value is relative to the computed font size of the document's root element, normally html. If that root size is 16px, then 1rem equals 16px, 0.75rem equals 12px, and 1.5rem equals 24px. The conversion is straightforward: divide pixels by the root size to obtain rem, and multiply rem by the root size to obtain pixels, as in 24px ÷ 16px = 1.5rem and 1.5rem × 16px = 24px. This tool lets you change the base, with 10px, 14px, and 16px presets, because a design system may deliberately use a different root size. Results are rounded to at most six decimal places, so 1px at a 3px base shows as 0.333333rem, and the base must be greater than zero.

16px is a common browser default for the root font size, but user preferences can change it and authors can override it. That flexibility is a reason to use relative units for text and the spacing around it: when the root size changes, a rem based layout can grow with it. This does not automatically make an interface accessible. Fixed heights, clipped overflow, or narrow containers can still break at larger text sizes. WCAG 2.2 success criterion 1.4.4 asks that text can be resized up to 200 percent without loss of content or functionality, so test with browser zoom and a larger default font size before treating a design as complete.

This tool converts only between px and rem, but the related em unit is worth knowing. An em is relative to the current element's font size for most properties. For font-size itself, it is relative to the parent's computed font size. Nested elements can therefore compound: a child set to 1.2em inside a parent set to 1.2em becomes 1.44 times the earlier size. rem avoids that compounding by always referring to the root. Yet em is useful for component details that should follow the component's own text size, such as an icon's width or a button's internal padding.

HEX, RGB, and HSL in a maintainable color system

HEX and RGB describe the same red, green, and blue channels in different notation. Six-digit HEX uses two hexadecimal digits per channel: #8178FF means red 129, green 120, and blue 255. Short HEX, such as #F0A, duplicates each digit: #FF00AA. RGB notation writes decimal channels directly, as in rgb(129, 120, 255).

This tool reads and writes the comma-separated form that CSS Color Level 4 calls the legacy color syntax. It accepts 3- or 6-digit HEX with or without the #, rgb() with three whole numbers from 0 to 255, and hsl() with a hue from 0 to 360 and percentage signs on saturation and lightness. It does not accept the space-separated modern form such as rgb(129 120 255), hue units such as deg, percentage RGB channels, or any alpha value. Colors with alpha, such as 8-digit HEX or rgba(), are rejected with a message rather than silently losing their transparency.

HSL represents a color by hue, saturation, and lightness. Hue is an angle around the color wheel, saturation describes intensity, and lightness moves between dark and light. HSL can be easier to adjust by eye when building a family of related colors. It is not, however, a promise of equal perceived brightness. The CSS Color specification's own example is blue, hsl(240deg 100% 50%), and yellow, hsl(60deg 100% 50%): both have 50% lightness, yet the yellow looks much lighter. When color contrast matters, evaluate the actual foreground and background pairing instead of relying on HSL lightness.

Conversions between RGB and HSL involve rounding. This tool rounds RGB channels to whole numbers and shows HSL with up to one decimal place, so #8178FF appears as hsl(244, 100%, 73.5%). At that precision, pasting the HSL text back returns the same RGB channels for every 6-digit HEX color. If you shorten it to whole numbers, a channel can shift: hsl(244, 100%, 74%) becomes #837AFF, not #8178FF. For exact interchange with a design source, keep the source's original value in your design tokens.

The Copy CSS Variable button copies a declaration such as --color-primary: #8178FF;, always in HEX. Custom properties are read elsewhere with var(), for example background: var(--color-primary);, and they can hold any valid value, so storing the rgb() or hsl() form instead works too. A token named for its role, such as --color-primary, is easier to change later than the same color repeated across many selectors.

Unix timestamps, UTC, local time, and ISO 8601

Unix time is the number of seconds since the Epoch, 1970-01-01 00:00:00 UTC, counted by a formula that ignores leap seconds. In JavaScript, Date.now() returns milliseconds since that same instant. That unit difference is the source of many integration bugs. For dates between September 2001 and November 2286, a seconds value has ten digits and a milliseconds value has thirteen.

The converter offers explicit Seconds and Milliseconds modes plus Auto detect. Auto detect treats any value whose absolute size is at least 100,000,000,000 as milliseconds and anything smaller as seconds. A millisecond timestamp between 31 October 1966 and 3 March 1973 is therefore misread as seconds, and a seconds value beyond the year 5138 is read as milliseconds. When an API specifies its unit, select that unit explicitly. The Use Current Time button fills in the current time in seconds and switches the unit to Seconds.

A timestamp represents an instant, not a time zone. The same instant can be shown as UTC or as the local wall time of a device; midnight UTC is 09:00 in a UTC+09:00 zone and 19:00 on the previous day in a UTC−05:00 zone. This tool shows three readings of each timestamp: your device's local time, a UTC string in the toUTCString() form ending in GMT, and an ISO 8601 string from toISOString(), which always ends in the UTC Z suffix. The local and UTC lines stop at whole seconds; the ISO line keeps milliseconds.

The date-and-time field uses a datetime-local input, which holds a date and time with no time zone. This tool passes that value to new Date(), and JavaScript treats a date-time string without an offset as local time on your device. Around daylight saving changes that can be ambiguous: some local times occur twice when clocks move back, and some never occur when clocks move forward, yet the input still accepts them. JavaScript resolves a repeated time to the earlier instant and moves a skipped time forward by the length of the gap. The Unix seconds result is rounded down to a whole second. For records that cross regions or must be audited, store an unambiguous UTC timestamp or an ISO string with an offset, plus the intended IANA time zone when the original local context matters.

Fractional seconds are also accepted. A Unix seconds value may include a decimal fraction, such as 1700000000.5, meaning half a second after the whole second. JavaScript dates store whole milliseconds, so this tool rounds to the nearest millisecond. A JavaScript date can only represent ±8,640,000,000,000,000 milliseconds around the epoch, so in seconds mode anything beyond 8,640,000,000,000 is reported as an invalid timestamp instead of a misleading date. The input takes digits with an optional leading minus sign and decimal point; exponent notation such as 1e12 is not accepted.

  1. Name the field with its unit when you control a schema, for example createdAtMs or expiresAtSeconds.
  2. Exchange ISO 8601 strings or unit-labeled epoch numbers rather than human-readable dates; JavaScript only guarantees one date string format, a simplification of ISO 8601, and other formats are implementation-defined.

Frequently asked questions

Is 1rem always 16px?

No. It equals the computed font size of the root element. 16px is a common browser default, but the root may differ because of user preferences or your CSS. Set the base field to your project's actual root size before copying values.

Should every pixel value become rem?

No. Relative sizing is useful for typography and scale-related spacing, while CSS pixels are still practical for one-pixel borders and details. Test the interface under zoom and text resizing to decide whether each measurement behaves as intended.

Why does HSL sometimes return a slightly different RGB value?

The HSL shown here keeps one decimal place, and pasting it back gives the original RGB channels. If you round the HSL to whole numbers yourself, converting back can move a channel by up to five steps out of 255. Keep the original source color when exact fidelity is required.

How can you tell whether an epoch number is seconds or milliseconds?

Read the source API's contract first. Present-day seconds timestamps have ten digits and millisecond timestamps thirteen, but Auto detect only compares the value with 100,000,000,000, so millisecond values close to 1970 and seconds values far in the future are misread. Use the explicit unit selector for reliable results.

Are inputs sent to a server?

No. The conversion code on this page makes no network requests; your values are processed by JavaScript in the browser tab. The page itself does load Google Fonts and the Google AdSense script, which make their own requests.

Do the converters work offline?

Once the page has loaded, conversions keep working without a connection, because they never call a server. The page does not install an offline cache, so it has to be opened online first.
