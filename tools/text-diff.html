Review changes without losing context

A line diff answers a focused question: which lines were added, removed, or left unchanged between two versions? Paste the earlier version on the left and the proposed version on the right. Use split view when nearby context matters and unified view when you want a compact patch-style narrative. The comparison runs in memory and does not execute code.

Consider a three-line configuration where only a timeout changes from 30 to 45 and a retry line is added. A line diff should show one removal, two additions, and the unchanged lines around them. If the formatter also reorders every property, the same logical change may look much larger. Normalize formatting before comparison when the review is about behavior rather than style.

A common mistake is assuming an unchanged line is safe because the context around it changed. Another is reviewing generated or minified files without first comparing the human-maintained source. A third is copying the diff itself into production instead of applying the intended edit to the original file.

Small, reviewable comparisons

Keep the input scoped to the decision. For a large codebase, version-control tools preserve file names, authorship, rename detection, and history better than a browser text comparison. This tool is most useful for a snippet, configuration block, generated response, policy paragraph, or message draft that needs an immediate visual check.

When comparing JSON, format both sides with the same indentation and stable property order if order is not meaningful. When comparing prose, decide whether wrapping should create new lines; a changed line break can obscure a one-word edit. For secrets or NDA material, follow the private-workflow guide and organizational policy before pasting anything.

Example review sequence

  1. Save or identify the authoritative earlier version.
  2. Normalize superficial formatting only when appropriate.
  3. Compare and read every added and removed line.
  4. Apply the change in the source system, then run its normal tests.

Copying a diff is useful for a discussion, but it does not preserve the full metadata of a commit. Treat the browser result as a review aid. Use the JSON Formatter for malformed data and the Unit Converter when a numeric change mixes units.

Handing off a comparison

When another person must review the result, include the source of each version, the goal of the change, and the verification already performed. A colored comparison without that context can show what moved while hiding why it moved. Preserve the authoritative files separately and avoid pasting confidential material into a public issue.

After approval, compare the saved final file once more against the intended version. This catches last-minute formatting edits and copy mistakes introduced between review and publication.

Line endings and whitespace

Windows, macOS, and Linux can encode line endings differently, while editors may add a final newline or convert tabs to spaces. Decide whether those differences matter before reviewing. This tool converts Windows (CRLF) and older Mac (CR) line endings to LF before comparing, so it does not show line-ending changes; use an editor or version-control diff that displays them when they matter. Normalize them only when the project permits it, and never hide an intentional indentation change in a language where whitespace affects behavior.

Record any normalization in the review note so the next comparison uses the same assumptions and does not reopen resolved formatting noise.

How the comparison works

The result refreshes shortly after you stop typing in either editor, and Compare Diff or Ctrl + Enter (⌘ + Enter on a Mac) runs it at once. The tool finds a shortest line-level edit sequence: the fewest removed and added lines that turn the original into the revision. Swap exchanges the two versions and compares them again.

Reading the result

In split view, old lines appear on the left and new lines on the right. A red line with a minus sign marks a deletion; a green line with a plus sign marks an addition. Unchanged lines appear in both columns, and where lines were replaced, the removed and added lines are paired row by row, with blank rows filling out the shorter side. Unified view puts the same sequence into one stream. Both views draw on one comparison result, so switching between them does not compare again. The additions and deletions counters count changed lines, rather than individual characters or words.

Copy Diff copies the unified sequence as plain text, with each line prefixed by +, - or a space. It contains no file names and no @@ hunk headers.

What counts as a change

The tool treats any pasted input as plain text, so JSON, HTML, CSS, JavaScript, logs, and prose all work. Lines must match exactly: a change of letter case, a trailing space, or a tab replaced by spaces makes the whole line count as one removal and one addition. Pressing Tab in either editor inserts two spaces, not a tab character. The comparison does not highlight changed characters within a line, and it does not check whether code is valid.

Line endings are the exception. The browser already reports an editor's text with CRLF and lone CR line breaks converted to LF, and the tool converts them again before comparing, so two versions that differ only in line endings show no changes. A final line break does count: text that ends with one gains an empty last line, which appears as an added or removed blank line.

Size limit

Comparisons are limited to 2,500 lines across both editors combined. Above that, the tool shows a limit message instead of a result, to keep the page responsive.
